## ✨ What it does

- **🎯 Claude Code in one step** — declares a `claude-code` agent preset plus an engine; select it and the session is driven by the local Claude Code CLI.
- **🧭 Native Plan bridge** — the session's DSH plan mode is mirrored into the CLI's plan permission mode. `ExitPlanMode` never treats the model's own "plan" as approval: the plugin reads the plan body from the CLI-owned plan file and asks a human through the DSH question UI, even under full access. A plan file changed during review, or a mismatched tool-use ID, is rejected again; only the main loop may write the native plan file, and a subagent cannot borrow that path.
- **🧾 Tool-call lifecycle** — the Mod's `tool.check`/`tool.call`, the SDK `PreToolUse` hook and `canUseTool` share one host gate keyed by the real tool-use ID. One file call dispatches the host `tools/pre-execute` exactly once, argument rewrites may only touch audited free fields, and the audit journal records tool name, call ID, ownership and outcome — never argument bodies.
- **📡 Live trajectory** — text, thinking, tool calls, and tool results stream into the DSH session as they happen (`agent/assistant-stream` frames plus the durable `assistant/message`).
- **📊 Context occupancy** — Claude Code's token usage and model context window are written to the session log (`assistant/message.usage` + `request/context`), so the GUI shows context pressure and composition like it does natively.
- **🔐 Approval bridge** — DSH mode and approval policy map onto Claude's `canUseTool`; only an in-workspace `blockedPath` in `workspace-write` can pass automatically. Under `read-only`, file tools and shell tools (`Bash`, or `PowerShell` on Windows) are denied outright (see Known limitations). `AskUserQuestion` uses the DSH question UI. Claude's **file tools** are additionally dispatched into the host's `tools/pre-execute`, so the host's change cards and hooks can see them and a host `deny`/`cancel` is honored (see Known limitations). This is not DSH's OS-level sandbox.
- **🧰 Claude-owned execution** — the preset is a routing key; Claude uses its own tools and context, and the preset's persona sections are forwarded explicitly. DSH preset tools are not automatically forwarded.
- **⏯️ Exact resume** — the Claude session id is persisted on the side (a sidecar table plus a private fact), so a resumed chat continues the *same* Claude session.
- **🌐 Subagent trajectories** — Claude's built-in `Agent`/`Task` children appear as one-shot, read-only child sessions with short task labels and real run status. Provider identity stays in the descriptor; automatic titles are not emitted without legitimate human source messages. DSH-native delegation remains on the native loop.
- **⌨️ Live input** — followups queue for the next turn, steer enters the live query, and inject does not start a query by itself. Explicit cancellation requests SDK interrupt before closing the query; message sources, images and delivery facts are preserved.
- **🧩 Capability-checked mods** — the packaged `dsh-bridge` mod loads only into the current Claude subprocess. It observes prompt composition and can optionally adapt goal tools, without changing global plugin settings or the DSH application archive.
- **🧾 Native catalog commands** — `/claude-context` shows the last CLI context summary, `/claude-commands` the observed command/skill catalog, `/claude-command status|cost` runs fixed read-only native builtins, and `/claude-skill <name> [args]` queues an allowlisted, SDK-observed skill as a human turn. Metadata is bounded and observational: it never grants execution. `status` fails explicitly when the current CLI returns `uncertain` rather than pretending to succeed.
- **🎛️ Live model/effort switching** — a `model/selection` change only affects subsequent **main** steps; subagents keep native routing and the CLI's own fallback choice is not reset.
- **🎯 Goal-driven automatic tasks** — a session on the Claude Code preset supports the same goal mode as the standard preset: type `/goal <objective>` and it advances round after round, with Claude reading the bridged `get_goal`/`update_goal` and closing the objective out (complete/blocked). Toggle with `engines.claude-code.goal.enabled`, on by default.

## 🚀 Install

Requirements: `dsh` **0.2.0-rc.2** (bundled with the desktop app), pnpm on PATH, and a working `claude` CLI (signed in) or `ANTHROPIC_API_KEY`.

```sh
# Install as a link (link:), never file: — pass the absolute path to this directory
dsh plugin --profile desktop add /absolute/path/to/dsh-claude-code
```

Installation adds the package to the profile's `dsh.profile.bundles` and applies its bundled `cordis.patch.yml` (the plugin row plus the preset declaration). Restart the desktop app afterwards.

> **Why not `file:`** — the `@deepseek-ai/dsh-scope` / `dsh-agent` / `dsh-session` modules this plugin
> imports must be the *same module instances* the host uses (`dsh-scope` tags a context with the
> module-private `Symbol("dsh.scope")`, so two physical copies are two different Symbols). DSH
> redirects peer-declared packages to the host's copy inside `app.asar` only for linked installs.
> `file:` copies the checkout into the profile along with its own `dsh-scope`, and every session
> then fails to create or resume with `Agent preset binding requires a scoped context`. See the
> [setup guide](docs/guides/setup.md). A linked install requires no reinstall after source edits;
> restart the desktop app to reload modules that are already loaded.

## ⚙️ Configuration

Edit `~/.dsh/profiles/desktop/cordis.patch.yml` and override by row id:

```yaml
- id: dsh-claude-code
  name: dsh-claude-code        # restate name whenever you override a row's config
  config:
    enabled: true
    routeMainLoop: true         # on by default; false leaves the preset visible but unrouted
    defaultEngine: deepseek
    engineByPreset: {}
    engines:
      claude-code:
        executable: claude
        persistSession: true
        includePartialMessages: true
        traceSubagents: true
        mods:
          enabled: true                  # capture only after the selected CLI passes offline checks
          handshakeTimeoutMs: 8000       # ready handshake before submitting user input
        goal:
          enabled: true                    # on by default: bridges the goal tools into Claude Code
          transport: mcp                   # mcp (default) / mod / auto; failures retain MCP
          blockedAfterConsecutiveRounds: 3 # consecutive rounds on one blocker before `blocked` is allowed
          # defaultMaxGoalRounds: 256      # optional: fallback when the model omits max_goal_rounds
        dshTools:
          enabled: false                 # opt in to native deliverables / jobs
          transport: mcp                 # mcp (default) / mod / auto; mod registers dynamically, falls back to MCP
          # names: [present, job_list, job_output, job_kill] # audited subset only
        env: {}
        contextWindow: 200000
        readOnlyBash: deny             # shell tools (Bash/PowerShell) under read-only: deny (default) / ask (per-command approval)
        # sandbox:                     # optional: pass the SDK SandboxSettings through (real sandbox on Linux/macOS only)
        #   enabled: true
```

| Key | Default | Meaning |
|---|---|---|
| `enabled` | `true` | Master switch; `false` leaves the native loop untouched |
| `routeMainLoop` | `true` | `false` keeps the global factory untouched: the preset is visible but sessions are not routed (safety valve, see index.mjs) |
| `defaultEngine` | `deepseek` | Engine for presets without a mapping; `deepseek` is the "native loop" sentinel |
| `engineByPreset` | `{}` | Explicit preset id → engine id overrides |
| `engines.<id>` | `{}` | Engine-private options, forwarded verbatim |
| `engines.claude-code.executable` | `claude` | Claude Code executable |
| `engines.claude-code.persistSession` | `true` | Reuse one Claude session across turns |
| `engines.claude-code.includePartialMessages` | `true` | Token-level streaming |
| `engines.claude-code.traceSubagents` | `true` | Map Claude's internal subagents to read-only DSH child sessions |
| `engines.claude-code.env` | `{}` | Extra environment for the claude subprocess |
| `engines.claude-code.contextWindow` | unset | Manual context window (tokens) fallback |
| `engines.claude-code.readOnlyBash` | `deny` | Strategy for shell tools (`Bash`, or the CLI's `PowerShell` on Windows) under read-only: `deny` outright (no prompt) / `ask` restores per-command approval |
| `engines.claude-code.sandbox` | unset | Passed through verbatim to the SDK `query()` `SandboxSettings`; nothing is passed when unset. Not DSH's sandbox, and inert on Windows |
| `engines.claude-code.mods.enabled` | `true` | Validate/test the selected CLI and load the packaged observer only into its subprocess |
| `engines.claude-code.mods.handshakeTimeoutMs` | `8000` | Pre-input ready timeout, 1–30000 ms; fallback starts a new MCP query without resending input |
| `engines.claude-code.goal.transport` | `mcp` | `mcp` for compatibility; `mod`/`auto` select mod when supported, otherwise MCP; never both in one query |
| `engines.claude-code.goal.enabled` | `true` | Whether to bridge `get_goal`/`create_goal`/`update_goal` into Claude Code (the session can auto-advance with `/goal`) |
| `engines.claude-code.goal.blockedAfterConsecutiveRounds` | `3` | How many consecutive goal rounds on the same blocker are needed before the model may mark it `blocked` |
| `engines.claude-code.goal.defaultMaxGoalRounds` | unset | Fallback round cap when the model calls `create_goal` without one (defaults to DSH's 256) |
| `engines.claude-code.dshTools.enabled` | `false` | Opt-in scope-aware DSH tool bridge, independent of goal transport |
| `engines.claude-code.dshTools.transport` | `mcp` | `mcp` for compatibility; `mod`/`auto` register dynamically when supported (`mcp__dsh-bridge__*`) and fall back to MCP; never both in one query |
| `engines.claude-code.dshTools.names` | `[present, job_list, job_output, job_kill]` | Audited subset only; an empty array registers no server; unknown names or a non-array fail the turn |

## ⚠️ Known limitations

- The preset is a routing key: Claude Code brings its own tools and persona. DSH tools are not forwarded unless explicitly selected by the opt-in bridge below. The preset's **persona sections are forwarded** item-by-item (see below); the host's tool-usage sections and runtime contexts are deliberately not.
- A session locks its preset once it has produced a turn (a DSH rule), so the engine can no longer be switched. Within a blank session, switching **away** from Claude Code (to `standard` or any native preset) swaps back to the native loop in place; switching a native session **into** Claude Code takes effect on the next resume (app restart or reopening the session), because the host recomposes presets in place without recreating agents.
- Claude Code's internal subagents are a **read-only projection**: they appear in the lineage tree as child sessions and carry no loop and no continuation. To make the panel report the right run state, each child also registers a **passive status-carrier agent** (no model loop, no input); the panel's running/completed/not-running labels come from the host agent registry alone.
- Exact resume depends on the plugin's sidecar store (`~/.dsh/dsh-claude-code/sessions.json`). If it is lost, a new Claude session may be created; restoration of the original model history is not guaranteed. **The same mapping is also recorded as a private fact** (`claude-code/session`, fsync'd and split per session), so a missed or half-written sidecar file no longer loses the continuation target: the table is consulted first, the fact second, and only when both are missing does the session start fresh (amnesia over connecting to the wrong session). **DSH forks do inherit Claude's history**: a forked session resumes the parent's Claude session with `forkSession`, so the CLI copies the transcript to a new session id — the fork remembers the conversation and the parent is not continued. If the parent has no recorded Claude session yet (or both records were lost), the fork starts fresh instead of guessing.
- **The host's `agent/pre-step` event is not dispatched.** That event is the native loop's prompt-assembly pipeline: workspace instructions, time snapshots, plan-mode sections and DSH-side automatic compaction all rewrite the assembled step there. This plugin generates its own prompt and the request that actually goes out is assembled by the Claude Code CLI, so DSH's assembly never reaches the wire. Adopting the event would inject workspace instructions twice (the CLI already loads them) and apply compaction/sections to nodes the model never sees. Cost: a goal round still lacks the standard driver's private reservation fence (see the limited plugin-side admission guard below), and goal rounds are not rendered as their own request series. Evidence and the listener inventory: `docs/superpowers/specs/2026-10-13-agent-pre-step-design.md`.
- **Claude's file tools are dispatched into the host's `tools/pre-execute` (a new host-visible surface).** `Write` / `Edit` / `MultiEdit` / `NotebookEdit` execute inside the CLI process and never pass through DSH's tool registry, so the plugin dispatches this waterfall for them from `canUseTool` (`lib/host-tool-gate.mjs`), using the host's payload shape (`name` as the wire name, `arguments`, `callId`, `agent`, `signal`, through the agent-scope dispatcher). Three consequences: (1) `dsh-workspace-changes`' pre-edit whole-file capture now works for plugin sessions — **change cards can appear even when the workspace is not inside any git repository** (verified live 2026-10-15: one `Edit` in a non-git workspace produced `Edited m4-notes.txt +1 -1`, with the real content in the "before" side of the diff; nothing else in that workspace could have supplied a before-image); (2) other host pre-execute listeners (e.g. `dsh-hooks-claude-code`'s PreToolUse hooks) now see these calls too — that is deliberate alignment with DSH's behavior; (3) a listener's `deny` / `cancel` rejects the call with the host's reason, an `ask` **suppresses every automatic allow** and lands on the DSH approval seam (it asks even under danger-full-access, because a listener explicitly demanded a human), and a throwing listener fails closed into a denial — the same semantics the host registry itself has. **Not covered:** `MultiEdit` (its input is an `edits` array) and `NotebookEdit` (`notebook_path`) are still dispatched, but the host recorder cannot derive a path from them and so produces no pre-edit capture (the plugin will not rewrite the arguments to satisfy the recorder; the host's own `mutationPath` was exercised offline against all four shapes). The dispatched exec also lacks the registry-minted `token` / `deferContext` / `concludeTurn`, so a listener that rewrites arguments or takes over execution through those fields has no effect in plugin sessions.
- **The Plan bridge and tool lifecycle work on real identity and real boundaries, never on type existence.** DSH plan mode (including `pending`) may only be committed as `plan/mode` at a real CLI main-step boundary; a read failure fails closed as unavailable instead of meaning inactive. `EnterPlanMode`/`ExitPlanMode` bypass the ordinary approval short-circuits, and full access still requires a real plan review. Review is bound to that one tool-use ID: a plan file changed during review, the DSH side having left plan mode, an oversized plan, or a body that does not start with a heading all re-deny; the model saying "plan approved" does not count. Only the main loop may write the plan file, and a subagent cannot borrow the parent's authority. On the tool side, one gate is keyed by the real tool-use ID: Mod identity arriving first and the SDK callback later merge into the same call; each call dispatches the host `tools/pre-execute` exactly once; rewrites may only touch audited free fields (other native constraints keep their original values) and can never change identity fields. Audit facts (`claude-code/tool-lifecycle`, `step-control`) record tool name, call ID, ownership, decision and outcome — not argument bodies, thinking, or tool results. **Zero-inference acceptance** (real CLI + local fixed Messages stub): one Write and one Edit each dispatched the gate once and asked for approval once; the rewritten argument actually landed on disk and the following Edit read the rewritten value (`.dsh-diag/native-runtime-*`, `externalInference:false`).
- **Native catalog commands are observation only and grant no execution.** `/claude-context` shows the last context summary (`tokens` is the API-reported value; categories are CLI estimates marked `estimated:true`, `detail:summary`); `/claude-commands` shows the SDK-observed command/skill catalog (capped at 128 commands, 128 skills, 512 characters per entry); `/claude-command status|cost` runs only fixed read-only native builtins, and `status` fails explicitly when the current CLI returns `uncertain` instead of pretending success; `/claude-skill` must be both allowlisted in configuration and currently observed by the SDK, and is queued as an ordinary human user input with arguments preserved. Catalog data is not execution authority, and it is not injected into DSH's native context breakdown (the host has no seam). Identity binding stays `unknown` when a child projection arrives before its SDK event and binds only on real spawn evidence; one child never gets two trajectories.
- **Live model/effort switching only affects subsequent main steps.** A session selection change is applied by the Mod's `turn.step` to the main query only; subagents keep the native model and the CLI's own fallback choice is not reset. This rewrites only changed fields; it does not open a new query or rebuild the session. All P1–P3 capabilities were verified against the real CLI with a local zero-inference stub for request fields and execution boundaries; **real paid generation, real summarization, and formal desktop/v4 lifecycle acceptance have not run** and must not be claimed as passed.
- **Native compact now has a scoped maintenance path; real summarization still needs separate acceptance.** The Claude Code preset's `/compact` acquires `runMaintenance`, resumes this session's exact Claude history, and dispatches the native command through `$.command.run({ command: "compact" })`. It sends no additional SDK user prompt, never calls the dormant LLM provider, and leaves DSH surface history intact. A separately loaded `dsh-compact-observer` reports structured completion with an observation-only token; command output is not proof of success. Busy agents, unsupported Mods, `persistSession:false`, missing history and unmaterialized forks fail explicitly. Cancellation, timeout or lost results after a claim remain uncertain and are never automatically retried. The maintenance deadline defaults to five minutes; `mods.maintenanceTimeoutMs` may shorten it. A **zero-inference probe on CLI 2.1.301 (2026-10-16)** reached manual compaction over resumed history with no SDK user input, returned a structured skip receipt, and made zero API requests. The probe intercepted the summarizer: this is **not** paid-summary, desktop, or full persistence acceptance. Direct `$.session.compact()` is still refused in SDK/headless mode despite its type declaration. CLI observations and maintenance receipts live in the separate `claude-code/compact` and `claude-code/native-operation` journals; the upstream must still support actual summary requests. DSH's native context breakdown still has no injection seam; obtaining CLI categories does not replace that panel. The pressure bar retains real usage/window data. Current design: `docs/superpowers/specs/2026-10-16-native-compact-mod-design.md`; the old-channel investigation remains in `2026-10-13-claude-compaction-design.md`.
- **Prompt snapshots are observations, not a final system prompt**: `claude-code/prompt-snapshot` records `observed-compose`, `partial` and `compositionLoop: unattributed`. Outer mods may still change the prompt, and the capture cannot prove a main-agent-only origin. Native `system/message` projection remains disabled.
- **The approval bridge is not DSH's execution sandbox, but `read-only` is enforced here.** Claude's built-in tools never pass through DSH's filesystem/process executors, so the DSH file sandbox's `writableRoots` does not constrain them. The plugin applies the sandbox mode itself: under `read-only`, `Write` / `Edit` / `MultiEdit` / `NotebookEdit` are **denied outright with no approval prompt** — there is no "allow once" escape hatch, matching standard sessions where a read-only session cannot modify files however it is approved. Under `workspace-write` an in-workspace `blockedPath` may be auto-allowed; `never` grants no write permission; full access keeps its existing behavior. **Shell tools under `read-only` follow the same path: denied outright by default**, because whether a given command writes a file cannot be decided statically and Claude's shell has no DSH file sandbox behind it — leaving an approval hatch would downgrade read-only to "click once and write". The cost is that even `ls` stops working in a read-only session; set `engines.claude-code.readOnlyBash: "ask"` to restore the old per-command approval. **The policy applies to whole tool names, so every platform's name must be listed**: on Windows this CLI reports its shell tool as `PowerShell` (there is no `Bash` in its `system/init` tool table), and live verification (2026-10-15, isolated web instance) caught what a missing name costs — in a read-only session `PowerShell`'s `Set-Content -Path probe.txt …` reached the approval seam, where "allow once" would have written the file; with the name added, the same call is denied outright (`read-only session denies PowerShell …`) and no prompt appears. **Commands the CLI itself judges read-only never reach `canUseTool`; that path is now covered by an SDK `PreToolUse` hook.** The same live run caught the escape: in a read-only session `Get-ChildItem` was executed by the CLI with **no** `approval/asked` between `tool/call` and `tool/result` — reading the plugin's own branches backwards, `canUseTool` was never called, so the read-only boundary did not exist for that class of execution. The hook is a second entrance: it fires for **every** tool call, shares the one read-only policy with `canUseTool` (`readOnlyDenial` in `lib/approval.mjs`, so both entrances produce the identical reason), and only ever denies — it never allows and never overrides a decision. Live re-verification on the same isolated instance: the same `Get-ChildItem` was denied by the hook (`PreToolUse:PowerShell hook error: dsh-claude-code: read-only session denies PowerShell …`, `isError: true`, **no** approval prompt), and after switching the session to "edit in workspace" the same command ran again immediately — the policy is read live, not a blanket denial. **Residual limit, stated honestly:** this is still **not OS-level isolation**, only a boundary at the tool-call layer — what an allowed tool does inside the CLI process (shell commands under `workspace-write`, calls made inside a subagent, anything the CLI executes without going through either entrance) is invisible to the plugin; with `readOnlyBash: "ask"` the hook deliberately abstains, so read-only commands the CLI auto-allows produce no prompt at all (`ask` only covers calls the CLI hands up); and the hook is itself a CLI callback — if some execution path does not invoke it either, the boundary still does not exist there, which the plugin cannot prove on its own.

- **The SDK sandbox is the only real sandbox available here, and it is neither DSH's nor on by default.** `engines.claude-code.sandbox` is passed through verbatim to the SDK's `sandbox` (`SandboxSettings`); when unset nothing is passed at all (identical to previous behavior). Three things to know: (1) it depends on host OS capability — Linux bubblewrap / macOS `sandbox-exec` — and does not apply on Windows; (2) it governs how the CLI process itself executes, a separate mechanism from DSH's sandbox mode and fs sandbox — the plugin never derives `read-only` from it, nor relaxes `read-only` because of it; (3) when a command is auto-allowed *inside* a real sandbox, `canUseTool` may never be called — but the read-only decision no longer depends on that callback: the `PreToolUse` hook fires for every call, so shell and file-mutating tools are still denied under `read-only` (live verification in the bullet above). A deployment that wants the sandbox itself to be the boundary sets `engines.claude-code.readOnlyBash: "ask"` (the hook abstains and the CLI's in-sandbox allowance stands). Configuring `sandbox` therefore does not make `read-only` stricter; the two are orthogonal.
- **Submission is not consumption**: replay is acknowledgment only; live human input grants goal authority only after a matching result UUID proves consumption. Unconfirmed input becomes `uncertain` and is not automatically replayed. `keepInbox` preserves unsubmitted pending input and recoverable reservations, not input already delivered to Claude. Initial and live batches reserve their original queue before dequeue and commit submission atomically; steer intent survives restart, while legacy next-step entries are not guessed to be querying. When an explicit stop ends a turn, retained pending input that can still form a turn (a queued follow-up or a querying steer) now starts automatically; pure injects still never open a turn.
- Capture failure emits a sanitized SDK notice, records `capture-disabled` and warns without changing the prompt or goal adapter. Each shared capability-probe caller can cancel independently of other active callers.
- **Paused goals require explicit recovery**: active/disarmed goals can be rearmed in an authorized human turn. Paused goals retain standard policy: use `/goal resume` or the goal play control. A chat message saying “continue” does not guarantee a paused goal resumes.
- Failed mod checks or startup readiness produce `claude-code/mod-status` and retain MCP. The selected CLI **2.1.296** passed offline checks; the SDK-bundled **2.1.220** rejected this mod's hooks format. The plugin does not upgrade the CLI automatically.
- **The session's selected model and reasoning level now reach Claude.** The latest `model/selection` event is folded and passed to the SDK query as `model` / `effort`, so switching models in the DSH picker actually changes what runs (previously the model came only from the CLI's own env/settings and the picker did nothing). An effort level the SDK does not define is not guessed or coerced. Models must therefore be ids the local Claude CLI can serve.
- **Subagents stay one-shot; they cannot be continued from here.** The SDK has no control request that addresses or resumes a subagent, and the CLI's `SendMessage` is a *model-facing tool* the plugin cannot call on its own. The only non-model channel is a mod hooking `SubagentStop`, which feeds a subagent more context when it stops — not "open the child and keep chatting". Structurally a subagent lives inside the live parent query, so once that ends the transcript is readable but not conversable. The catalog therefore keeps `mode: "one-shot"` rather than label the UI differently. **Unblocking this one sits on Claude Code's side**: the CLI would have to expose a subagent session address (or let the parent process send a `SendMessage` on its behalf) before the plugin has any non-model channel to attach to. Details: `docs/superpowers/specs/2026-10-13-continuable-subagent-design.md`.
- **The DSH tool bridge is opt-in and audited.** Set `engines.claude-code.dshTools.enabled: true` to register agent-visible `present` / `job_list` / `job_output` / `job_kill` as `mcp__dsh__*`. `names` can only narrow that set; no dynamic tools, DSH bash/fs, or job-start are exposed. Host `wireSchemas(agent).schemas` takes precedence, respecting PTC's `run_code` collapse; `z.fromJSONSchema` adapts the complete object at the SDK boundary. Calls forward the CLI's real tool-use ID, recheck query lifetime, cancellation, exact live agent identity and tool visibility, then enter the host's `execute(exec)` gate. Missing CLI identity fails closed; finished queries invalidate old handlers. **This parent-agent bridge is main-query-only:** the main transcript must confirm the same ID and tool name; inherited subagent calls and unknown ownership are denied rather than borrowing the parent's cwd, delivery session or jobs owner. Early MCP requests wait at most five seconds for confirmation, with cancellation/close cleanup. A real isolated web instance verified delivery cards, file previews and native v4 logs; real SDK registration and argument validation have regression coverage. **These are DSH registry jobs, not Claude's own background tasks.** Host completion notices still use the native inbox. The bridge forwards no host prompt sections itself and does not replace the standard loop. Design and acceptance: `docs/superpowers/specs/2026-10-14-dsh-tool-bridge-design.md`.
- **Host persona is forwarded item-by-item; the rest of the host prompt assembly is not.** The plugin deliberately never dispatches `agent/pre-step`, so nothing `systemPrompt.assemble()` produces reaches Claude automatically. The deployment persona sections (`deployment:persona-prefix/suffix`) written in the preset are read explicitly, interpolated with the host's own variables and appended to the CLI preset (`systemPrompt.append`, see `lib/host-persona.mjs`). Tool-usage sections (they describe *DSH's* tools) and runtime contexts (they describe *DSH's* sandbox/approval boundary, while what actually applies in Claude Code mode is this plugin's permission/approval strategy) are deliberately not forwarded. A missing service, a failed assembly, an unresolved variable or a section marked `complete` all degrade to "not forwarded" with a reason — a literal `{{cwd}}` is never sent to the model. **Skills are not in this category**: they are not a prompt section but DSH's `skill` tool (`@deepseek-ai/dsh-skill-filesystem` + `@deepseek-ai/dsh-tool-skill`), so covering them is a new tool-bridge entry requiring separate audit and approval.
- **Limited goal-log admission guard:** automatic goal inputs are checked against the host's public state before preparation, after asynchronous preparation, and at the native log boundary. Initial SDK delivery rechecks the admitted round, including after mod readiness or MCP fallback. Automatic goal input during an active query is unsupported and rejected before submission. Existing followup, steer, inject, and keepInbox semantics are preserved. A read failure is not an absent goal or renewed continuation authority; submitted or uncertain inputs are never automatically replayed. Recovery checks native registration evidence to avoid duplicate `user/message` events. This is a limited plugin-side admission guard, not the standard driver's private reservation/stale/content/fiber fence, and it does not repair historical logs. Offline Session/v4 replay does not replace separately approved live Claude or host-lifecycle acceptance.
- **Goal continuation depends on the goal stack in the DSH host plane** (`dsh-goal` + `dsh-goal-round-driver`). On deployments without that stack `goal.enabled` silently does nothing (no tools bridged, no prompt added), and `/goal` falls back to DSH's native behavior (there is no `/goal` command at all if that preset doesn't mount `command-goal`).
- **A Windows `.cmd`/`.bat` shim that cannot be unwrapped is refused instead of handed to the SDK.** The npm-installed `claude` is usually a batch shim, and mid-update the executable it points at may not be on disk. The Claude Agent SDK decides whether to start a script with node by extension alone, so it spawns `.cmd` as a native executable and Node (since CVE-2024-27980) throws `spawn EINVAL` synchronously — the user sees an errno and neither the file nor the fix. The plugin now skips unwrappable shims during resolution and keeps scanning PATH for a spawnable candidate; when only a shim remains it refuses the turn with a readable error naming the path and the fix (`cannotSpawnDirectly` in `lib/auth.mjs`).
- **Images inside tool results are no longer dropped, but only the trajectory view draws them as pictures.** When Claude's `Read` opens an image, the receipt is a `tool_result` with inline base64; the old code dropped that block, so the user saw a model describing an image the UI never showed. The bytes now go to the host attachment store (`ctx.get("attachments").saveImages`) *before* the message reaches the tracer, and the event keeps only a durable reference — `{type:"image", attachment:{attachmentId, mediaType, width, height, bytes}}`, no base64 in the session log. A missing attachment service, a URL source, an unsupported shape or a failed save each degrade to a **text placeholder naming the reason**; nothing is ever silently dropped (see `lib/tool-result-images.mjs`). **Live check (2026-10-15, isolated web instance):** reading a 64×64 PNG put the bytes under `<DSH_HOME>/attachments/v1/objects/…`, and the **trajectory view's tool detail "result" pane rendered the real image** (the tool row is labeled `图片 ×1`; the DOM holds a 64×64 blob image). The **conversation view still prints that block as JSON**: DSH's image gallery card admits only the native `read_image` call shape plus its model-facing envelope text, while Claude's `Read` maps to `read` and produces no such envelope, so it takes the generic card (`resultText`: non-text blocks as pretty JSON). Reaching the gallery would mean forging DSH's native tool identity and envelope text — text the gallery then displays to the user — i.e. inventing content, so it is not done. Recorded as-is: `data.meta` may still carry the CLI's own `file.base64` (images below the 16 KiB cap land in the log, larger ones drop the whole meta); no frontend code reads that field.

## 🛠️ Image input troubleshooting

`session/attachment-invalid` / `MODEL_DOES_NOT_SUPPORT_IMAGES` is a DSH admission rejection, before the Claude Code plugin receives the message. For a custom model alias configured through `@deepseek-ai/dsh-llm-pi-ai`, declare `input: [text, image]` on the **specific model entry** only if its upstream supports images. The configuration key is `input`, not the resolved metadata field `inputModalities`; unknown custom models without a declaration conservatively default to text-only. This belongs to the host provider configuration, not `engines.claude-code`. Do not enable images provider-wide for a mixed catalog or bypass the admission guard. Reload the configuration or restart DSH and verify model metadata; passing admission does not prove the upstream gateway accepts images.
